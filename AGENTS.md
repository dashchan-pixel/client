# AGENTS.md

The **main app** of the Dashchan rework — an Android imageboard browser that dynamically loads separate **extension APKs** (one per imageboard, built from a sibling `extensions` repo).

## Build

- Build with the **Gradle wrapper** directly: `./gradlew assembleRelease` / `assembleDebug` / `installRelease` (adb) / `clean`.
- Signing is handled in `build.gradle.kts`: the `release` config auto-signs from `keystore.properties` (or `KEYSTORE_FILENAME` env), else falls back to the debug key. No wrapper script needed.
- Gradle 9.6, AGP 9.2, Kotlin DSL (`build.gradle.kts` / `settings.gradle.kts`), Java 17. **100% Kotlin** — `compileReleaseJavaWithJavac` compiles nothing (AIDL still generates Java, registered by AGP).
- minSdk / compile / target = **36** (Android 16). Target = **arm64-v8a only**.
- `allWarningsAsErrors` is on — **the release build must stay warning-clean.**

## Source map

- `src/chan/**` — the **extension API surface** (`@Public` / `@Extendable`). The extension APKs link against these signatures. **Never change a `@Public` declaration's nullability** (field type, method param/return). Private fields and internal helpers are fair game.
- `src/com/mishiranu/dashchan/**` — the app itself (`ui`, `content`, `widget`, `media`, `graphics`, `util`).
- `media/VideoPlayer.kt` — Media3 (ExoPlayer) facade; keeps the old partial-file streaming model via a custom `DataSource`. Replaced the retired ffmpeg JNI player + Webm `.so` extension.
- `chan/http/**` — networking on **OkHttp 5**, keeping the old chan HTTP API shape. Kept: manual redirect policy, single-connection throttling, `FirewallResolver` (Cloudflare/anti-DDoS). Removed: custom sockets, WebSocket, GMS hacks.
- `content/net/Proxy*.kt` — a forum's proxy is nothing but its own settings, and `ProxyConnection` is the single line a script reads and writes them as (`scheme://user:password@host:port`, the form every service hands its endpoint out on). **No proxy service has code in the app and none should be given any**: changing the IP a forum is seen at is a `UseIn.APP` command flagged `autoRun`, which `VisibleIpCommand` finds for a forum and runs from the three places that ask — the forum's settings row, the toast a banned post puts up, and a script calling `chan.changeVisibleIp()`. The app's whole part is dropping the pooled connections afterwards, which a script cannot do. The per-service `ProxyProvider`/`ProxyService`/`AsocksService`/`DataImpulseService` layer this replaced is in the history if a detail is ever wanted back — both services live on as importable commands in `docs/commands/`.
- `ui/posting/PostingFragment.kt` + `widget/PostingSheetLayout.kt` — the submission form has two hosts: a bottom sheet **added over** the page so the thread can be read behind it, which is what it is by default, or the content fragment it has always been, *replacing* the page, which is what *Classic style* (`Preferences.KEY_POSTING_CLASSIC`, off until asked for, and the one thing `Preferences.isPostingSheet` reads) puts back. Which one it is comes from the activity (`PostingFragment.sheet`, set in `MainActivity.navigatePostingSheet`), never from the fragment reading the setting — a form restored from the fragment stack is hosted plainly and must not think it is still a sheet. `handleBackPress` is the one exception: a stacked form that *was* a sheet comes back as one, over the page `navigateFragment` stacked under it as it left, so that returning from a pushed screen lands where the user was rather than a back press short of it. Two things follow from a sheet being a second fragment in `content_fragment`: `MainActivity.currentFragment` (topmost) is the sheet while `screenFragment` is the page under it, and **everything a page publishes to the activity must go through `screenFragment`** or it will cast the sheet to `PageFragment`; and the sheet owns no toolbar — no title, no menu item, its markup bar inline (so *markup buttons at the bottom* greys out while the sheet is on — with no toolbar there is nothing for the other value to mean), its attach action a button at the end of the checkbox row, and no section headers. `PostingSheetLayout` is an `ExpandedScreen.Layout` that then uses neither the padding nor the margins that interface is usually about: **the view fills the screen and the insets are the sheet's**, the toolbar's as a ceiling on the sheet's height and the navigation bar's as the footer's bottom padding. Taken as margins on the view instead, the sheet stops a navigation bar short of the bottom of the screen and the page shows through the strip below SEND; and a sheet inset by `expandedOffset` inside a full-height parent hangs that far off the *bottom* of the screen, taking the send button with it, which is why they are not padding either. **A sheet's height is its own**, worked out in `PostingSheetLayout.onMeasure`: the form's content height clamped to between 30% of the room below the toolbar and all of it, or that room in full, with the form given exactly what the drag handle above and the send button below leave. Leaving that to a `wrap_content` sheet and a weighted form to squeeze looked equivalent and was not — a sheet grown into the top of its parent overshot it by the send button's row. **Where a sheet that is up sits is asserted in `onLayout` too, not left to the behavior**, which offsets the sheet by a top edge it worked out from the height the sheet had when it last laid it out: a sheet that has grown since — dragged taller, or a captcha arriving — grows *downwards* instead, and what goes over the bottom edge is the row with SEND in it. So the form is *not* the last row of the scrolling posting layout in a sheet: `footer_container` is reparented into `PostingSheetLayout.footer`, which is what keeps SEND on screen at every height. The comment field is the *weighted* row of a sheet's form (the `ScrollView`'s `fillViewport` plus `layout_weight` on the comment wrapper), so the room a form shorter than the sheet is not using is a taller field rather than a gap above the captcha — `resizeComment`'s filler-height pass is for the plain host only, and running both would just fight. Resizing by dragging the handle is this view's own gesture, not `BottomSheetBehavior`'s (a sheet as tall as its content has nowhere above to slide to, so the behavior clamps an upward drag away to nothing): the sheet's top edge follows the finger, and letting go animates the height to whichever of the two stops is nearer. A sheet also only drags by its content when that content opts into nested scrolling, which a plain `ScrollView` does not do by itself. One trap that is not the sheet's alone: **a `ClickableToast` outlives the fragment that put it up**, so a toast button's action goes through `PostingFragment.whileOnScreen` — a sheet swiped away while its toast still stood made "Details" and "Change" crash on a detached fragment.
- `widget/FloatingToolbar.kt` + `ui/navigator/PageFragment.kt` — the far end of the toolbar, moved down to the thumb: a small bar in the bottom corner, painted the toolbar's colour and carrying the toolbar's icons, holding a thread's *Reply* and *Contents* and a board's *New thread* and *Refresh* — plus a ⌘ for the `UseIn.APP` commands in scope, wherever the bar is already up. **The menu is still where an action lives**: a page names the items it hands over (`ListPage.floatingActions`, a slot plus a menu item id plus an icon attribute, since an overflow item is allowed to have no icon of its own), and `PageFragment.updateFloatingToolbar` reads them *out of the menu the page has just prepared* and hides them there. So one visibility rule serves both places — an item the page hid is no more in the bar than in the toolbar, search mode empties the bar the same way it empties the toolbar, and a *Contents* that is a submenu stays one, dropped from the button as a `DropdownPopup`. Nothing is held onto between a prepare and a tap: the menu item is looked up again by id, because a menu can be rebuilt in between. The bar's own two gestures are why it handles touch at all: **a long press then a drag reorders it** — the press is the button's own long click, the drag is the bar's from the first movement, and until the finger lifts the buttons only *translate*, because reordering the views live sends `removeView` through the very view being touched and cancels the gesture — and **a two finger tap turns it between horizontal and vertical**, caught at the second finger's `ACTION_POINTER_DOWN` before a button can read it as a press. Both are the user's rather than a page's, so both are kept in `Preferences` (`floating_toolbar_order`, by slot name, and `floating_toolbar_vertical`) and a slot no page offers today keeps its place in the order for the day one does. The view added to a page is a full-size *transparent* container with the bar in a corner of it: that is what makes the insets `ExpandedLayout` hands its children the bar's margins rather than its padding (padding would grow the bar, not move it off the navigation bar), and a touch that misses the bar falls through to the list, which is the point of a bar that floats over content. Floating over content is also why the list is given room for it: the bar reports the height it reaches (`FloatingToolbar.onContentInsetChanged`, a button plus the bar's padding, times the buttons in a column when it stands vertical, plus its margin twice) and `ExpandedLayout.setExtraBottom` adds that to the *recycler view's* bottom padding — the list's, so the last item still scrolls up through the strip instead of ending under the bar, and the list's alone, because padding the floating container would push the bar up by the room it was being given. An empty bar reports 0, so a page that offers nothing pads nothing.
- `res/**` — **density-qualified folders are intentionally gone**: every bitmap has been redrawn as a `<vector>` in plain `res/drawable/`, so there is nothing to bucket. Add new icons as vectors; don't reintroduce `drawable-*dpi/` PNGs. The launcher lives in `res/mipmap-anydpi/` (no `-v26` — adaptive icons are unconditional at minSdk 36).
- `lang/values*/strings.xml` — user-facing strings. **Every new string must be translated in the same change**, not left for later: add it to `lang/values/` *and* to `values-ru`, `values-it`, `values-pt-rBR`. Keep the alphabetical order of each file, and reuse the wording an existing string already established for the same concept (e.g. ru "Тред", pt-rBR "Fio" for *thread*).

## Git / workflow

- **`rework` is the default branch** (origin `dashchan-redacted/client`, `origin/HEAD → rework`). Push/publish only with explicit user OK.
- To recover pre-conversion Java when a warning/NPE is suspect:
  `git show "$(git log --format=%H --diff-filter=D -1 -- <path>.java)^:<path>.java"`
- **`.gitignore` is an allowlist** (`/*` then `!/…`) — a new top-level file won't be tracked until it's explicitly allowlisted.

## Traps left by the Java→Kotlin conversion

The J2K converter systematically inserted `!!` / non-null casts where Java handled `null` gracefully — turning fallbacks into crashes and making the original null checks show up as "always true/false" warnings. Several shipping NPEs have already been found this way.

- **Never delete a "dead" null check or silence a warning with `!!`** without recovering the original Java and matching its semantics. `!!` *is* correct where the Java dereferenced unconditionally.
- **The `!!` de-noising campaign is ongoing** (~3,079 left by J2K, clustering on a few hundred nullable field *declarations* — fix the declaration and use sites collapse, compiler-proven). `scripts/hot-nullables.sh` ranks declarations by `!!` pressure.
- **The cheap wins are gone** (slices A–R, ~3,079 → ~1,380). The early slices retired dozens of `!!` per declaration; the ranking now tops out around 60 and falls into single digits, spread across ~170 files. What remains is per-site work, and a growing share of it is *correct* — expect later slices to land 20–40, not 200. **Raw `!!` count is no longer a good proxy for remaining work.**
- **Decision rule:** a field null-checked *anywhere* (`if`, `?.`, `?:`) is an optional — keep it nullable, hoist `val x = this.x ?: return`. Only a field used *exclusively* through `!!` is a `lateinit` candidate. **Never turn an unguarded `x!!.foo()` into `x?.foo()`** — that hides a crash as a silent no-op.
- **Useful tell:** when one call site of a method `!!`s an argument and a sibling site doesn't, the outlier is usually the J2K artifact. That's how `ThreadsPage`'s `applyFilter(query!!)` was caught — `ArchivePage` called the same nullable-accepting method clean.
- Gotchas: `CommonUtils.toArray` returns **null for an empty collection**; `ChanConfiguration.getTitle()` is nullable by design.

**Out of scope — do not "fix":**

- `chan/content/model/Post.kt` (56 `!!`, the hottest file in `chan/`) is **done**. It is a two-state class — `builder` XOR `postNumberCompat`, one per constructor — and the Java dereferenced `builder` unguarded in every accessor; only `getPostNumber()` branches. Every `!!` is faithful. It will keep topping the count; leave it. Rewriting those into `?.` would silently change `@Public` ABI behaviour.
- More generally, `chan/` was swept in slice K and its residue is largely load-bearing. New effort belongs in `com/mishiranu/dashchan/`.

## Lint & inspections

- Use **`./gradlew lintRelease`** (report: `build/reports/lint-results-release.{html,xml,txt}`). `assembleRelease` only gates FATAL, so a green build can still hide non-fatal errors.
- **`lintRelease` is error-clean — keep it that way.** Warnings are not gated (~300 left, led by `UseKtx`, `NotifyDataSetChanged`, `RtlHardcoded`, `MissingQuantity`).
- Suppressed on purpose, each with its rationale at the site: `AppCompatCustomView` (disabled in the `lint {}` block — the app is framework-widget/framework-theme based and ThemeEngine does the tinting, so custom views extend the platform classes), `RestrictedApi` on `MainActivity.dispatchKeyEvent`, `GestureBackNavigation` in `DialogStack` (gestures go through its `OnBackAnimationCallback`; the key path keeps long-press "clear all"), `JavascriptInterface` in `HeadlessJsEngine` (bridges are typed `Any`), `QueryAllPackagesPermission` in the manifest (extensions are found by scanning installed packages for a chan/lib `<uses-feature>`).
- Media3's `@UnstableApi` marker is `androidx.annotation.RequiresOptIn`, which **only lint enforces** — Kotlin compiles unstable usage silently. `VideoPlayer` opts in once at the class.
- **JSON is formatted too**: `jsonCheck`/`jsonFormat` (`jq --indent 4 .`, matching `[*.json]` in `.editorconfig`) hang off `ktlintCheck`/`ktlintFormat`, so `./gradlew ktlintFormat` fixes it and the pre-commit hook rejects it. Requires `jq` on PATH; the task also fails on JSON that does not parse.
- **detekt is a gate of its own, and only the pre-commit hook runs it** (`scripts/git-hooks/pre-commit` → `compileDebugKotlin ktlintCheck detekt`; its header comments say what each is for). A compile plus `ktlintCheck` can pass and the commit still be rejected — e.g. `UseCheckOrError` wants `error("…")` where a `throw IllegalStateException("…")` was written. Config in `detekt.yml`; `!!` is advisory only, reported by `detektDoubleBang` without failing. Existing findings are frozen in `detekt-baseline.xml` — **never regenerate the baseline to silence a new one.**

## Deliberate design — do NOT fix

- Custom `X509TrustManager` (`chan/http/HttpClient.kt`) + two `onReceivedSslError` handlers (`ui/BrowserFragment.kt`, `content/service/webview/WebViewService.kt`) **proceed despite SSL errors on purpose** — required for the firewall/Cloudflare bypass. Lint flags it as a MITM exposure; that's expected. Leave it.
